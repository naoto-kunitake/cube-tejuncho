# coding-style

機械で守れる規則は ESLint と Prettier に入れてあり、ここには人 (と Claude) の判断が要る規則だけを置く。
既存のコードと食い違うときは、この規約を正として直す提案をする。

## 考え方

- 読みやすさを最優先にする。明確な名前と素直な構造で、賢さや短さを狙わない
- 実際に動く最も単純な解を選ぶ。先回りの抽象化と早すぎる最適化をしない
- 繰り返しが 2 か所目に現れてから共有に切り出す。1 か所のうちは抽出しない
- 使われていないコード・設定・依存を「後で使うかも」で残さない

## 命名

- 識別子は英語。日本語の概念との対応は CLAUDE.md の用語表に従い、同じ概念に別の英語を使わない
- 真偽値は `is` `has` `can` で始める。関数は動詞で始める (`normalizeAlg`, `loadDocument`)
- `UPPER_SNAKE` は本当の定数 (プリセットの一覧、上限値) だけ
- 略語 (`btn` `cfg` `idx`) とローマ字 (`tejun`) を使わない。ファイル名は `project-structure` に従う

## コメントと JSDoc

- コメントは「なぜ」だけ。型・名前・処理から読めることは書かない。迷ったら書かない
- 書いてよいもの: 外部の制約 (ライブラリの仕様、ブラウザの挙動)、一見おかしく見える意図、参照した規格やトークン名
- JSDoc は原則なし。引数の意味が型から読めないときだけ 1 行。`@param` `@returns` の機械的な列挙はしない
- 経緯 (「最初は A だったが B にした」) はコミット本文に書き、コードには残さない

## 関数の設計

- 引数のオブジェクトや配列を書き換えず、新しい値を返す。副作用が要る関数は名前でそれと分かるようにする (`saveDocument`)
- 深い入れ子より早期リターン。三項演算子を入れ子にしない。複数条件は `if` / `switch` に分ける
- 意味のある数 (閾値、遅延、上限) には名前つき定数を使う
- 1 つの関数は 1 つの責務。長くなったら責務の境界で分ける

## 型

- `any` を使わない。外部からの入力は `unknown` で受け、type predicate か Zod で絞り込む
- `as` と `!` (非 null 断言) を使わない。型が合わないときは型か設計を直す
- 取りえない組み合わせを型で表せないようにする。`{ loading, data, error }` のような矛盾しうる形ではなく判別ユニオンにする
- 名前つき export だけ。`export default` と `export *` を使わない
- 配列の添字で得た `undefined` を `??` の既定値で黙らせない。長さが決まっているならタプルで表し、起こりえないなら `throw` にする
- 取りうる値の集合は `as const` の配列を 1 か所に置いて正とし、型も Zod のスキーマもそこから導く。同じ並びを 2 か所に書かない

## 非同期とエラー

- 回復できる失敗 (記法の検証、読み込む JSON の検証) は `Result<T, E>` で返し、呼び出し側に成否の確認を強制する。`Result` は `lib/result.ts` の自作の判別ユニオン (ライブラリは入れない)
- `throw` は本当の異常 (バグ、回復できない状態) だけ。`catch` は `unknown` で受けて絞り込む
- 失敗を握りつぶさない。利用者に見せる文言は `copy.ts` から取り、内部の詳細は `console.error` に残す
- 独立した非同期処理は `Promise.all` で並列に。順序が要るものだけ `for...of` で直列に

## テスト

- 1 テスト 1 事実。名前は日本語の文 (「Ri を R' に直す」) で、何が成り立つかを言い切る
- 入出力だけを見る。内部の実装や呼び出し回数を検証しない
- snapshot を使わない (差分が読めない)
- 画面に依存しないロジックは必ず単体テストを書き、実装と同じコミットに入れる。画面は描画して落ちないことを 1 本。筋書きのテストはデータの安全に関わるものだけ
- 見本データは本番のデータ (プリセットなど) を使わず、テストファイルの中か隣の `fixtures.ts` に書く (本番のデータを直すとテストが落ちる)
